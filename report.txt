== STAGE 1 ==

Concurrency issues:
1. The command buffer, as a consumer-producer problem. 
2. The registration table, as reader-writer problem.

Solutions:
1. Solved by using semaphores and mutexes to access the command buffer as seen in class for the consumer producer buffer. Each time a command is to be executed, it is first produced and put into the buffer and then it's consumed.
2. Solved with a read-write lock, for accessing the table.

Tests: Stage 1 passed all the tests follow, performance and stress, with streaming, and no known bugs.


== STAGE 2 ==

Concurrency issues:
1. (5.1.1) Operations FOLLOW (reads received client info and writes on the followed client_bundle), TIMELINE (reads timeline and clears it in client_bundle) and PUBLISH (writes on the timeline of the publisher client (cl) and all its followers, then updates disconnected clients of cl).

Solutions:
1. For the independent requests of multiple client threads to run in parallel, there is the need for a lock per client. To implement this we chose to use mutexes that are saved in a structure (lock_struct) that keeps both the already initialized mutex and the associated client key (initialized with 0 on the start of the server). These structures are saved in a buffer (buffer_lock). We didn't choose read-writer locks as they wouldn't do much benefit since all operations are mostly writing operations. There is also the need to use a mutex to synchronize interactions with buffer_lock. There are 3 different instances which use client locks and, consequently, the buffer_lock:
a. When a client is created we associate its client key to a lock in buffer_lock (through the lock_struct), in the first position of the buffer found with the key set to 0 (meaning it was free).
b. When locking a client, to run the operations mentioned above, we first look for the lock of the corresponding client on the buffer, searching by its key, and secondly, we use the mutex to lock and unlock.
c. When a client is removed, the key associated to the lock by is reset to 0.

Tests: Stage 2 passed all the tests follow, performance and stress, with streaming, and no known bugs.
